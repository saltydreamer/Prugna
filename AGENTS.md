=== .ai/boilerplate rules ===

# Boilerplate conventions

## Stack

- Laravel 13 + Fortify (headless auth) + Spatie Permission + Inertia v3 + Vue 3 (`<script setup>`, plain JS) + Vuetify 4 + Ziggy. Database: MariaDB (SQLite in-memory for tests).
- UI copy is Italian. Server-side strings go through `__()`; validation messages live in `lang/it`.

## Authorization

- Permissions are defined ONLY in `App\Enums\Permission`; system roles in `App\Enums\Role`. After adding a case run `php artisan permissions:sync` (also called by the seeders).
- `super-admin` owns every permission through `Gate::before` in `AppServiceProvider`, but policies (`UserPolicy`, `RolePolicy`) still apply their structural rules (no self-delete, system roles not deletable, last super admin protected).
- Authorize in controllers with `$this->authorize()` / Form Request `authorize()`; the frontend uses `usePermissions().can()` only to hide UI.

## Notifications

- Every in-app notification extends `App\Notifications\AppNotification` and implements `title()` / `message()` (optionally `icon()`, `color()`, `actionUrl()`, `actionLabel()`). It is stored in the database and also mailed when the user enabled `email_notifications`.
- Notifications are queued (`ShouldQueue`): a worker must run (`composer dev` starts one).

## Registry (Anagrafiche)

- `Organization` (soft deletes = "archiviata", read-only until restored) has many `Location` (sedi) and `Contact` (contatti). Routes under `registry.*`; locations/contacts are nested and scoped (`scopeBindings`).
- Exactly one primary location/contact per organization, enforced by `App\Models\Concerns\HasPrimaryFlag` (first record is primary, deleting the primary promotes another).
- Italian fiscal data: `App\Rules\ItalianVatNumber` / `ItalianTaxCode` validate check digits; normalize with their `normalize()` before storing.
- Customers and suppliers are separate registries: `Organization::role` (`OrganizationRole` customer|supplier, never both; changeable only while no document refers to it, `hasDocuments()`). Lists/create pages at `registry.customers.*` and `registry.suppliers.*` (same `OrganizationController`, role from the route default); show/edit/nested routes stay `registry.organizations.*`. Pickers use `organizationOptions(OrganizationRole)`; sales documents validate `role = customer`, supplier orders `role = supplier`.
- Permissions `organizations.*` (customers) and `suppliers.*` (suppliers), chosen by `OrganizationRole::permission()`; `OrganizationPolicy` also covers locations and contacts (update on the organization).
- Nested API resources returned inside another resource must be `->resolve()`d, otherwise Inertia wraps them in `data`.

## Catalog (Prodotti e servizi)

- `Product` (type product/service, unit `UnitOfMeasure`, optional `BillingPeriod` for recurring services only), `ProductCategory`, `VatRate` (0% rates need a FatturaPA `nature` N1–N7 and a legal reference), `CustomerPrice` (fixed price OR discount % per organization, optional expiry).
- Always compute the price for a customer with `App\Actions\Catalog\ResolvePrice` (agreed price > agreed discount > list price; expired agreements ignored).
- Money: decimal(12,4) columns cast to strings; the frontend formats with `formatMoney()` from `@/utils/format`.
- Codes are generated by `Product::nextCode()` (P00001 / S00001) when left empty.
- Large option lists for dialogs are `Inertia::optional()` props loaded with `router.reload({ only: [...] })` when the dialog opens.

## Settings

- `App\Support\Settings` (scoped singleton, cached): key/value settings edited in Impostazioni (`company.*`, `mail.*`, `quotes.*`, `fiscal.*`). `mail.password` is stored encrypted and never sent to the frontend.
- SMTP from the UI is applied by `App\Support\MailSettings` when the mail manager is resolved; saving restarts queue workers.
- `PaymentTerm` (FatturaPA method MPxx, days, end of month); organizations have a default `payment_term_id`.

## Quotes (Preventivi)

- `Quote` + `QuoteLine` (types item/section/text, optional lines counted only when selected). Always save through `App\Actions\Quotes\SaveQuote` (numbering PRV-00001, customer snapshot, totals) and compute totals with `QuoteTotals` (mirrored in `resources/js/utils/quoteTotals.js`).
- Status flow: draft → sent → accepted/rejected; sent quotes past `valid_until` become expired via `quotes:check-expiry` (scheduled daily, also reminds owners 3 days before). Only drafts are editable/deletable; accepted quotes are final.
- Visibility: owners see their own quotes; `quotes.supervise` sees everyone's (`Quote::visibleTo()`, `QuotePolicy`).
- Customers answer on the public page `/q/{public_token}` (no login, rate limited); the owner gets `QuoteActivityNotification`.
- PDF: `App\Support\QuotePdf` + `resources/views/pdf/quote.blade.php` (dompdf, DejaVu Sans with font subsetting).

## Orders and invoices (Ordini e Fatture)

- Shared document infrastructure: `DocumentTotals` (line rounding + VAT per rate), `SyncDocumentLines` (replace lines freezing VAT), `DocumentNumber::next()` (yearly numbers `ORD-2026-0001`, `FT-2026-0001`, `NC-2026-0001`, row lock + unique index), `CustomerSnapshot`, `IsDocumentLine`.
- `Order` + `OrderLine` (`quantity_invoiced`): created from an accepted quote with `SaveOrder::fromQuote()` (one per quote) or by hand. Customer and lines are editable only while nothing is invoiced (`Order::isEditable()`); `refreshInvoicedQuantities()` recomputes from invoices (drafts included) minus issued credit notes. Permissions `orders.view` / `orders.manage`; PDF "Conferma d'ordine" via `OrderPdf`.
- `Invoice` + `InvoiceLine` (types invoice TD01 / deposit TD02 / credit_note TD04, series FT/NC). Build drafts with `BuildInvoice` (from quote: full/deposit; from order: full/selection/deposit; credit note), save with `SaveInvoice` (freezes regime, withholding and pension fund from `fiscal.*`, keeps the "Rimborso imposta di bollo" system line in sync), issue with `IssueInvoice` (`problems()` lists what blocks issuing; numbering only at issue time, chronological order enforced). Issued invoices never change: correct them with a credit note.
- Fiscal totals: `InvoiceCalculator` (pension fund on the taxable, withholding, split payment, virtual stamp duty > 77.47 €), mirrored in `resources/js/utils/invoiceTotals.js`. Deposits are deducted in the balance as negative system lines (`deducts_invoice_id`), only once issued.
- FatturaPA XML: `App\Support\FatturaPa\FatturaPaXml` (FPR12/FPA12). Strings must be Basic Latin/Latin-1 (`text()` transliterates). `FatturaPaXmlTest` validates against the official XSD in `tests/Fixtures/fatturapa`.
- Permissions `invoices.view`, `invoices.manage` (drafts), `invoices.issue` (issue, credit notes). PDF courtesy copy via `InvoicePdf` (`resources/views/pdf/invoice.blade.php`, all PDFs extend `pdf/layout.blade.php`).

## Purchases (Acquisti) and rebilled costs

- `PurchaseOrder` + `PurchaseOrderLine` (numbering `OF-2026-0001`, statuses draft/sent/confirmed/received/cancelled), saved with `SavePurchaseOrder`. Optional `order_id` (customer order; forces `customer_id` to its customer) and `customer_id` (who the costs are charged to). Lines are at cost; `rebill` + `markup_percent` mark costs to charge back (ignored without a customer). Permissions `purchases.view` / `purchases.manage`. PDF via `PurchaseOrderPdf` (never shows customer or markup); email via the generic `App\Mail\DocumentMail` + `DocumentSendDialog.vue`.
- Rebilling: `App\Actions\Purchases\RebillCosts` lists pending costs (`PurchaseOrderLine::toRebill()`: rebill lines of sent/confirmed/received orders without an invoice line, credit notes excluded) and builds the invoice line (`purchase_order_line_id`, net cost + markup, same VAT). Offered in the invoice editor (`RebillCostsDialog`, endpoint `sales.invoices.lookup.costs`) and when invoicing an order (`include_costs`). `InvoiceRequest` checks customer, committed status and single use; credit notes drop the link. Supplier orders with charged-back lines are frozen (`PurchaseOrder::isEditable()`).
- Order page shows costs and estimated margin (revenue + markups − costs not charged back).

## Expenses (Spese) and documents read by AI

- `Expense` + `ExpenseLine` (types invoice / receipt / credit_note, `ExpenseCategory`, `PaymentMethod`, `due_date`, `paid_at`; scopes `unpaid()` / `overdue()`), saved with `SaveExpense` (supplier snapshot, lines, totals, attachment on the private `local` disk). Supplier must have role supplier; the same supplier number per year can't be recorded twice. Optional `order_id` / `customer_id` + line `rebill` / `markup_percent`: charged back like supplier order lines (`RebillCosts` handles both sources, keys `po-ID` / `ex-ID`, invoice lines carry `expense_line_id`). Permissions `expenses.view` / `expenses.manage`.
- Document reading: `App\Support\Ai\DocumentReader` stores the upload and returns an `AiExtraction` (status, result, model, tokens, cost, time). FatturaPA XML / .p7m are parsed by `App\Support\FatturaPa\FatturaPaReader` (no AI); photos (shrunk to 2000 px) and PDFs go to `OpenRouterClient` (chat completions, `response_format` json_schema strict, `provider` with `require_parameters` and `data_collection: deny` / `zdr`, PDFs via the `file-parser` plugin). Schemas and instructions in `DocumentSchemas`; drafts built by `ExpenseDraft` / `OrganizationDraft` (supplier matched by VAT/CF, customers never used as suppliers, VAT rates mapped, total checked). Nothing is saved until the user confirms the prefilled form (`?extraction=ID`).
- Settings `ai.enabled`, `ai.api_key` (encrypted, never sent to the frontend), `ai.model` (chosen from the live OpenRouter catalog, cached 6 h), `ai.privacy`. Permission `ai.use` (XML import doesn't need it). In tests fake `openrouter.ai/*` with `Http::fake`.

## Frontend

- Pages: `resources/js/pages/**` (lowercase directory, e.g. `admin/users/Index`). Layout is chosen automatically in `resources/js/app.js` (`auth/*` → `AuthLayout`, else `AppLayout`).
- Reusable components: `resources/js/components`; composables: `resources/js/composables`.
- Links: use `useInertiaLink().link(route('name'))` with `v-bind` on Vuetify components (`v-btn`, `v-list-item`...).
- Toasts: server side `Inertia::flash('toast', ['type' => 'success', 'message' => '...'])`; client side `useToast()`.
- Confirmations: `await useConfirm().confirm({...})`.
- Shared props: `auth` (user, roles, permissions), `inbox` (unread_count, latest), `app`, `status` (Fortify).
- Component defaults (variants, density...) are set once in `resources/js/plugins/vuetify.js`.

## Quality

- `php artisan test` (feature tests per area in `tests/Feature`), `vendor/bin/pint`, `npm run lint`, `npm run format`.

# Laravel Boost Guidelines

## Foundational Context

This application is a Laravel application running on PHP 8.3. Always use the APIs that match the installed major version of each package — do not assume a version.

Before relying on a package's API, confirm its installed version:
- PHP packages: run `composer show --direct` to list direct dependencies with versions, or `composer show <vendor/package>` for a single package.
- JS packages: check `package.json` for the installed versions.

## Conventions

- You must follow all existing code conventions used in this application. When creating or editing a file, check sibling files for the correct structure, approach, and naming.
- Use descriptive names for variables and methods. For example, `isRegisteredForDiscounts`, not `discount()`.
- Check for existing components to reuse before writing a new one.

## Verification Scripts

- Do not create verification scripts or tinker when tests cover that functionality and prove they work. Unit and feature tests are more important.

## Application Structure & Architecture

- Stick to existing directory structure; don't create new base folders without approval.
- Do not change the application's dependencies without approval.

## Frontend Bundling

- If a frontend change doesn't show in the UI or you get a "Unable to locate file in Vite manifest" error, run `npm run build` or ask the user to run `npm run dev` or `composer run dev`.

## Documentation Files

- You must only create documentation files if explicitly requested by the user.

# Laravel Boost

## Project Rules

- This project contains committed, area-grouped rules in `.ai/rules` when that directory exists, including path-scoped framework guidelines under `.ai/rules/boost`. Before you enter plan mode or create/edit any file, you MUST first: open @.ai/rules/index.md (it maps file globs to rule files), read every rule file whose globs cover the path(s) in scope, and run `grep -rin 'keyword' .ai/rules` to catch what a path match alone misses. Do not write code until you have read and are following every matching rule. If `.ai/rules` does not exist, continue without it.

## Artisan

- Run Artisan commands directly via the command line (e.g., `php artisan route:list`). Use `php artisan list` to discover available commands and `php artisan [command] --help` to check parameters.
- Inspect routes with `php artisan route:list`. Filter with: `--method=GET`, `--name=users`, `--path=api`, `--except-vendor`, `--only-vendor`.
- Read configuration values using dot notation: `php artisan config:show app.name`, `php artisan config:show database.default`. Or read config files directly from the `config/` directory.

## Tinker

- Execute PHP in app context for debugging and testing code. Do not create models without user approval, prefer tests with factories instead. Prefer existing Artisan commands over custom tinker code.
- Always use single quotes to prevent shell expansion: `php artisan tinker --execute 'Your::code();'`
  - Double quotes for PHP strings inside: `php artisan tinker --execute 'User::where("active", true)->count();'`

# PHP

- Always use curly braces for control structures, even for single-line bodies.
- Use PHP 8 constructor property promotion: `public function __construct(public GitHub $github) { }`. Do not leave empty zero-parameter `__construct()` methods unless the constructor is private.
- Use explicit return type declarations and type hints for all method parameters: `function isAccessible(User $user, ?string $path = null): bool`
- Use TitleCase for Enum keys: `FavoritePerson`, `BestLake`, `Monthly`.
- Prefer PHPDoc blocks over inline comments. Only add inline comments for exceptionally complex logic.
- Use array shape type definitions in PHPDoc blocks.

=== inertia-laravel/core rules ===

# Inertia

- Inertia creates fully client-side rendered SPAs without modern SPA complexity, leveraging existing server-side patterns.
- Components live in `resources/js/pages` (unless specified in `vite.config.js`). Use `Inertia::render()` for server-side routing instead of Blade views.
- ALWAYS use `search-docs` tool for version-specific Inertia documentation and updated code examples.
- IMPORTANT: Activate `inertia-vue-development` when working with Inertia Vue client-side patterns.

# Inertia v3

- Use all Inertia features from v1, v2, and v3. Check the documentation before making changes to ensure the correct approach.
- New v3 features: standalone HTTP requests (`useHttp` hook), optimistic updates with automatic rollback, layout props (`useLayoutProps` hook), instant visits, simplified SSR via `@inertiajs/vite` plugin, custom exception handling for error pages.
- Carried over from v2: deferred props, infinite scroll, merging props, polling, prefetching, once props, flash data.
- When using deferred props, add an empty state with a pulsing or animated skeleton.
- Axios has been removed. Use the built-in XHR client with interceptors, or install Axios separately if needed.
- `Inertia::lazy()` / `LazyProp` has been removed. Use `Inertia::optional()` instead.
- Prop types (`Inertia::optional()`, `Inertia::defer()`, `Inertia::merge()`) work inside nested arrays with dot-notation paths.
- SSR works automatically in Vite dev mode with `@inertiajs/vite` - no separate Node.js server needed during development.
- Event renames: `invalid` is now `httpException`, `exception` is now `networkError`.
- `router.cancel()` replaced by `router.cancelAll()`.
- The `future` configuration namespace has been removed - all v2 future options are now always enabled.

=== laravel/core rules ===

# Do Things the Laravel Way

- Use `php artisan make:` commands to create new files (i.e. migrations, controllers, models, etc.). You can list available Artisan commands using `php artisan list` and check their parameters with `php artisan [command] --help`.
- If you're creating a generic PHP class, use `php artisan make:class`.
- Pass `--no-interaction` to all Artisan commands to ensure they work without user input. You should also pass the correct `--options` to ensure correct behavior.

### Model Creation

- When creating new models, create useful factories and seeders for them too. Ask the user if they need any other things, using `php artisan make:model --help` to check the available options.

## APIs & Eloquent Resources

- For APIs, default to using Eloquent API Resources and API versioning unless existing API routes do not, then you should follow existing application convention.

## URL Generation

- When generating links to other pages, prefer named routes and the `route()` function.

## Testing

- When creating models for tests, use the factories for the models. Check if the factory has custom states that can be used before manually setting up the model.
- Faker: Use methods such as `$this->faker->word()` or `fake()->randomDigit()`. Follow existing conventions whether to use `$this->faker` or `fake()`.
- When creating tests, make use of `php artisan make:test [options] {name}` to create a feature test, and pass `--unit` to create a unit test. Most tests should be feature tests.

=== pint/core rules ===

# Laravel Pint Code Formatter

- If you have modified any PHP files, you must run `vendor/bin/pint --dirty --format agent` before finalizing changes to ensure your code matches the project's expected style.
- Do not run `vendor/bin/pint --test --format agent`, simply run `vendor/bin/pint --format agent` to fix any formatting issues.

=== phpunit/core rules ===

# PHPUnit

- This project uses PHPUnit. Create tests with `php artisan make:test --phpunit {name}`.
- Do not include the test suite directory in `{name}`. Use `SomeFeatureTest`, not `Feature/SomeFeatureTest`.
- Read the `testing-best-practices` skill for guidance on coverage, naming, structure, dependency isolation, and review.

## Running Tests

- Run the narrowest set of tests that covers the change. Pass a file path or `--filter=testName` to `php artisan test --compact`.
- Rerun a test after each change to it.
- Run `vendor/bin/phpunit` to call the test runner directly. It accepts the same file path and `--filter=testName` arguments.
